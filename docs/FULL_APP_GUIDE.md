# The Ultimate `manage-system` Guide

This document explains everything in this repository in plain prose: every file, every function, every important variable, where each piece of data is created, and where it travels afterward. File paths are exact and relative to the repo root. Line numbers reflect the state of the code at the time this was written; they may drift slightly as the code evolves, but they're a reliable starting point for finding the thing being described.

If you want quick diagrams of the request flow instead of an exhaustive walkthrough, read `docs/APP_FLOW.md`. This document is the long-form companion to it, meant to be read start to finish like a reference book.

---

## Chapter 1 — The shape of the repository

At the root of the project sits `app/`, the Flask application itself. Inside it, `app/main.py` acts as both the application's entry point and the home of every server-rendered HTML route; it is the file Flask actually boots (`FLASK_APP=app.main`). Alongside it, `app/database.py` holds the single shared SQLAlchemy object used everywhere in the codebase, and `app/telemetry.py` wires up OpenTelemetry tracing, Prometheus metrics, and structured logging. Four feature folders sit next to these core files: `app/auth/` handles login, JWT verification, and talking to Keycloak's admin API; `app/products/` owns the `Product` model and its JSON API; `app/stock/` owns stock movements and the logic for changing quantities; `app/reports/` exposes read-only aggregate endpoints; `app/audit/` silently records every change made to products and stock movements; and `app/users/` exposes a JSON API for managing Keycloak users, without having any user table of its own. Templates for every page live under `app/templates/`, organized into subfolders that mirror the feature folders.

Outside `app/`, `migrations/` holds the Flask-Migrate (Alembic) history that built the database schema step by step. `keycloak/realm-export.json` is the entire identity provider configuration — every role, every group, every demo user, every OAuth client — imported automatically when the Keycloak container starts. `tests/` contains four different kinds of tests: fast unit tests that run against an in-memory SQLite database, a contract test suite driven by Schemathesis against the generated OpenAPI spec, data-integrity tests that require a real Postgres instance, and Playwright end-to-end tests that drive a real browser through a real Keycloak login. A separate `tests/k6/` folder holds JavaScript load and stress tests for k6.

`scripts/` is a grab-bag of bash and Python helpers used by local development, by the GitHub Actions pipeline, and by a self-hosted Jenkins pipeline, ranging from "wait until Keycloak is ready" to "free up ports held by a stale CI run." `observability/` contains the configuration for the entire monitoring stack: Prometheus scrape targets and alerting rules, Grafana datasources and dashboards, and Loki/Tempo/Alertmanager configs. `jenkins/` contains a custom Jenkins Docker image, its Configuration-as-Code file, and an entrypoint script.

At the very top level you'll find two Docker Compose files — `docker-compose.yml` for full local development including the whole observability stack, and the leaner `docker-compose.ci.yml` used by both CI systems — plus a single `Dockerfile` that builds the Flask app's image, a `Jenkinsfile` describing the Jenkins pipeline, and `.github/workflows/ci.yml` describing the GitHub Actions pipeline. `requirements.txt` pins the Python dependencies, `pytest.ini` configures the test runner, and `generate_openapi_spec.py` produces `openapi_spec.json`, the OpenAPI document that the contract tests fuzz against.

## Chapter 2 — How the pieces run together

When you bring the full stack up, Docker Compose starts a dozen or so containers that all talk to each other over a single shared network, resolving one another by service name through Docker's built-in DNS. The `web` container, named `flask_app`, is built from the repository's `Dockerfile` and listens on port 5000; it is the Flask application itself. Next to it sits `db`, a plain `postgres:16` container named `postgres_db` on port 5432, which holds not only this application's own tables but also Keycloak's internal schema — in the full development stack, both share the same database. The `keycloak` container, named `keycloak_auth` and built from the official Keycloak 24.0.1 image, listens on port 8080 and is the identity provider for the whole system; it imports its realm configuration from `keycloak/realm-export.json` on startup.

Around these three core services sits the observability stack: Prometheus on port 9090 scrapes metrics from Flask, Postgres, the host machine, and its own internal exporters; Grafana on port 3000 renders dashboards over Prometheus plus two other backends, Loki (port 3100) for logs and Tempo (port 3200) for distributed traces; Grafana Alloy, listening on ports 4317 and 4318 for OpenTelemetry data and exposing a UI on port 12345, acts as the collector that receives trace spans from Flask and also tails every container's Docker logs to forward them into Loki; Alertmanager on port 9093 receives firing alerts from Prometheus and would route them to notification channels, though those channels are currently stubbed out with empty configuration; node-exporter and postgres-exporter feed host-level and database-level metrics into Prometheus.

Three more services exist behind Compose "profiles," meaning they don't start with a plain `docker compose up` and must be explicitly requested: an `e2e` service running the Playwright test suite from inside a container with host networking so it can reach `localhost:5000` and `localhost:8080` directly; a `zap` service running an OWASP ZAP baseline security scan; and a `pip-audit` service scanning Python dependencies for known vulnerabilities. A fourth profile, `jenkins`, builds and runs a self-contained Jenkins server from the `jenkins/` folder, useful for running the full CI pipeline locally rather than relying solely on GitHub Actions.

## Chapter 3 — Where every environment variable comes from and where it goes

Configuration flows into the app through a `.env` file at the repository root, loaded two ways: Python's `python-dotenv` package calls `load_dotenv()` at the very top of `app/main.py` (line 22) so every environment variable is available to the process, and Docker Compose independently reads the same file via its `env_file: .env` directive for the `web`, `db`, and `keycloak` services. A template lives at `.env.example` with placeholder values and explanatory comments.

The Postgres credentials — `POSTGRES_USER`, `POSTGRES_PASSWORD`, and `POSTGRES_DB` — are defined once in `.env` and referenced from three places: the `db` service's own environment in `docker-compose.yml`, the `postgres_exporter` service's connection string, and Keycloak's `KC_DB_*` settings, since Keycloak shares the same Postgres instance in the full development stack. Separately, `DATABASE_URL` is the actual SQLAlchemy connection string that Flask uses; it's read at `app/main.py:29` and assigned directly to `app.config['SQLALCHEMY_DATABASE_URI']`. `FLASK_APP` tells the Flask CLI which module to run (`app.main`) for both `flask run` and `flask db upgrade`. `FLASK_SECRET_KEY`, read at `app/main.py:28` with a fallback of the literal string `"super-secret-key"`, signs the session cookie — this is what makes the cookie tamper-evident, though not encrypted, so nothing sensitive should ever be stored inside it (a lesson this project learned the hard way, discussed later in the authentication chapter).

Three variables control observability as a whole: `OTEL_ENABLED`, checked throughout `app/telemetry.py`, is the master switch — when it isn't the string `"true"`, the `/metrics` endpoint never gets registered and no trace spans are exported, though structured logging to stdout still happens regardless. `OTEL_EXPORTER_OTLP_ENDPOINT` tells the tracer where to send spans, defaulting to `http://alloy:4318/v1/traces`. `OTEL_SERVICE_NAME` becomes the `service.name` resource attribute attached to every trace, defaulting to `manage-system`.

The largest cluster of environment variables concerns Keycloak, and the split between them reflects a recurring theme in this codebase: some URLs must be reachable by the user's browser, and others must be reachable only from inside the Docker network. `KEYCLOAK_ISSUER` and `KEYCLOAK_AUTHORIZE_URL` are set in `docker-compose.yml` to point at `localhost:8080`, because the browser itself needs to load Keycloak's login page and cannot resolve the internal Docker hostname `keycloak_auth`. These feed into `app/auth/views.py` at lines 19 and 27, where Authlib is configured with them. By contrast, `KEYCLOAK_TOKEN_URL`, `KEYCLOAK_USERINFO_URL`, and `KEYCLOAK_JWKS_URL` all point at `http://keycloak_auth:8080/...` — the internal Docker DNS name — because these calls happen server-to-server, from inside the Flask container, and never touch the browser. They're consumed at `app/auth/views.py` lines 21 through 23, and `KEYCLOAK_JWKS_URL` is also read directly in `app/auth/middleware.py`'s `get_keycloak_public_keys()` function, where it falls back to deriving the certs URL from `KEYCLOAK_REALM_URL` if the JWKS variable isn't set.

`KEYCLOAK_CLIENT_ID` and `KEYCLOAK_CLIENT_SECRET`, read in `app/auth/views.py` at lines 16 and 17, configure the OAuth client used for the login flow itself; since the realm defines `flask-backend` as a public client, the secret is left empty in practice. A second, related variable, `KEYCLOAK_TOKEN_CLIENT_ID`, is used specifically inside `app/auth/keycloak_admin.py`'s `fetch_user_access_token()` function when the admin UI needs to mint a demonstration JWT for some user — this is a separate code path from the interactive login flow, even though it authenticates against the same client.

A final cluster of Keycloak variables governs the Admin API integration used by the `/users` feature: `KEYCLOAK_ADMIN_API_URL` gives the base URL for administrative REST calls, consumed by `_admin_base_url()` in `app/auth/keycloak_admin.py`; `KEYCLOAK_ADMIN_TOKEN_URL` gives the token endpoint on Keycloak's `master` realm, consumed by `_token_url()`; `KEYCLOAK_USER` (or `KEYCLOAK_ADMIN`) and `KEYCLOAK_PASSWORD` (or `KEYCLOAK_ADMIN_PASSWORD`) are the actual admin credentials used by `get_admin_access_token()` to log in as an administrator before every single Admin API call — notably, this token is fetched fresh every time rather than cached, unlike the JWT-verification public keys described later. `KEYCLOAK_ADMIN_CLIENT_ID` defaults to `admin-cli` if unset, and `KEYCLOAK_REALM` defaults to `inventory-realm` if unset.

## Chapter 4 — Booting the application

The first sixty-odd lines of `app/main.py` are the application's bootstrap sequence, and their order matters more than it might first appear. After the imports, `load_dotenv()` runs at line 22 to populate environment variables before anything else reads them. A plain `Flask` instance is created at line 24 with its template folder pointed at `app/templates`. Immediately afterward, `CORS` is applied to every route with `origins: "*"` — a deliberate choice reflecting that this application's JSON API is meant to be called directly with tools like `curl`, as demonstrated throughout `docs/CHEATSHEET.md`, rather than being locked down to a specific browser origin the way a production API serving only its own frontend typically would be.

The secret key and database URI are set next, at lines 28 and 29, followed by a handful of `flask-smorest` configuration keys that control the title, version, and Swagger UI path of the automatically generated API documentation, served at `/docs`. Then comes `init_oauth(app)`, imported from `app/auth/views.py` and called at line 41 — this must run before any request tries to use `oauth.keycloak`, since that's the point at which Authlib's OAuth client is actually registered. Right after that, `db.init_app(app)` binds the single shared SQLAlchemy object (from `app/database.py`) to this specific Flask app, and `Migrate(app, db)` wires up the Flask-Migrate command-line tools that make `flask db upgrade` work.

`init_telemetry(app, db)` and `init_metrics(app)`, both from `app/telemetry.py`, run next; the former sets up structured logging, request hooks, and OpenTelemetry tracing, while the latter — conditionally, only when `OTEL_ENABLED` is true — sets up Prometheus counters and registers the `/metrics` endpoint. `Api(app)` then creates the flask-smorest wrapper that will host every blueprint's automatically generated OpenAPI documentation.

Only after all of that does `register_audit_listeners()` run, at line 53 — this call, from `app/audit/listeners.py`, attaches SQLAlchemy event listeners to the `Product` and `StockMovement` models so that every insert, update, or delete on either table automatically produces a row in the `audit_logs` table. It has to happen before any write to those tables occurs, though in practice nothing in this codebase writes at import time, so the exact placement mostly matters for clarity rather than correctness. Finally, each blueprint — `stock_bp`, `reports_bp`, `products_bp`, `auth_bp`, `audit_bp`, and `users_bp` — is registered with the `api` object at lines 58 through 63, which is what actually makes their routes reachable.

## Chapter 5 — The database layer

The entire database layer rests on a single object. `app/database.py` is three lines long: it imports `SQLAlchemy` from `flask_sqlalchemy` and instantiates it once, as a module-level variable named `db`. Every model file — `app/products/models.py`, `app/stock/models.py`, and `app/audit/models.py` — imports this same `db` object rather than creating its own, and `app/main.py` binds it to the Flask app with `db.init_app(app)`. `app/telemetry.py` also imports it directly, using `db.engine.pool` to expose live connection-pool metrics as Prometheus gauges.

The actual connection string comes from the `DATABASE_URL` environment variable, assigned into `app.config['SQLALCHEMY_DATABASE_URI']` at `app/main.py:29`. In the Docker Compose stacks this points at the `db` service; in the test suite, `tests/conftest.py` overrides it to `sqlite:///:memory:` before importing `app.main` at all, since Python only executes module-level code once per process and the app object is built the moment the module is imported.

## Chapter 6 — Authentication and authorization

This is arguably the most intricate part of the codebase, split across three files that each handle a distinct concern: `app/auth/views.py` handles the interactive OAuth2 login and logout flow a human goes through in a browser; `app/auth/middleware.py` handles verifying JSON Web Tokens presented directly to the API and gating both API and UI routes by permission; and `app/auth/keycloak_admin.py` is a client for Keycloak's own administrative REST API, used to create users and manage their roles from within this application's own admin screens.

### The login and logout flow

`app/auth/views.py` defines the `auth_bp` blueprint, mounted at the `/auth` prefix, and a module-level `oauth = OAuth()` object from Authlib that isn't tied to any particular request — it's configured once, at application startup, by the `init_oauth(app)` function defined at lines 11 through 29. That function registers a client named `keycloak` with Authlib, supplying the client ID and secret, the browser-facing authorize URL, the server-to-server token and userinfo and JWKS URLs, and an explicit `issuer` value that Authlib checks against the token's own claims to guard against issuer confusion between the browser-facing and internal Keycloak URLs.

Visiting `GET /auth/login-page`, handled at lines 31 through 34, simply renders `templates/login.html`, a static page containing a single link to `/auth/login`. That second route, defined at lines 36 through 39, is where the OAuth dance actually begins: it computes the callback URL with `url_for('auth.callback', _external=True)` and calls `oauth.keycloak.authorize_redirect()`, which sends the browser off to Keycloak's own login form.

The real complexity lives in the callback handler, `GET /auth/callback`, spanning lines 41 through 76. The first thing it does is call `oauth.keycloak.authorize_access_token()`, which exchanges the authorization code Keycloak just sent back for a full set of tokens by calling `KEYCLOAK_TOKEN_URL` — a purely server-to-server call the browser never sees. If that exchange fails for any reason, the error is logged, `record_auth_failure(request.remote_addr)` is called to increment a Prometheus counter defined in `app/telemetry.py`, and the browser receives a JSON five-hundred response.

Assuming the exchange succeeds, Authlib has already parsed the ID token and made its claims available as `token.get('userinfo')`. The interesting part comes next: the code decodes the raw access token a second time, without verifying its signature, purely to read the `realm_access.roles` claim. This is necessary because Keycloak's realm roles — things like `product:view` or `stock:manage` — are not exposed through the standard OAuth2 `scope` string, which for this application only ever contains `openid profile email`; the actual permissions live in a completely different part of the token. The code filters that role list down to only the entries containing a colon, discarding Keycloak's own built-in roles like `offline_access` or `default-roles-inventory-realm`, and keeps the result as `user_scopes`.

What happens next is the result of a bug that was found and fixed during this project's development, and it's worth understanding in detail because it shapes how the session is structured today. The obvious approach would be to store the entire token dictionary — access token, refresh token, ID token, and all — directly in the Flask session, so that later code could use it if needed. But Flask's default session implementation is a signed cookie stored entirely in the browser, and browsers cap cookies at roughly four kilobytes. A full OAuth token bundle, with its access token, refresh token, and ID token all being independently-sized JWTs, comfortably exceeds that limit. When it did, browsers silently dropped or truncated the cookie, which manifested as users appearing to log in successfully and then immediately being treated as logged out on the very next page load — the session looked like it "loaded then disappeared." The fix, visible in the comment at lines 69 through 71, was to store only what the UI actually needs: the parsed `userinfo` dictionary under `session['user']`, and the filtered permission list under `session['user_scopes']`. The full token is explicitly removed from the session with `session.pop('token', None)` in case any earlier code path had put something there. After that, the browser is redirected to `/` — deliberately as a redirect and not a JSON response, so that refreshing the resulting page doesn't re-submit anything or trigger CSRF errors.

Logging out, at lines 78 through 92, clears the Flask session outright and then redirects the browser to Keycloak's own logout endpoint, passing along the client ID and a `post_logout_redirect_uri` pointing back at this application's home page — this ensures Keycloak's own single-sign-on session is terminated too, not just this application's local session. This logout URL was originally hardcoded to `http://localhost:8080` with an un-encoded redirect parameter, which broke the moment the application was reachable from any other hostname — Keycloak would either reject the URL outright or choke on the unescaped `&`/`:` characters inside it, surfacing as a confusing "invalid URI" error. It's since been fixed on both counts: the base URL is read from a `KEYCLOAK_LOGOUT_BASE` environment variable (still defaulting to the same `http://localhost:8080/...` value, so nothing changes for local development), and the redirect parameter is properly percent-encoded with `urllib.parse.quote`. The Cloudflare tunnel chapter later in this book explains exactly how and when `KEYCLOAK_LOGOUT_BASE` gets pointed somewhere other than localhost.

### Verifying JWTs and gating access

`app/auth/middleware.py` is the file responsible for deciding, on every single request, whether the caller is allowed to do what they're asking to do — and it does this in two entirely separate ways depending on whether the request is hitting the JSON API or a browser-facing UI page.

At the top of the file, a module-level variable `_public_keys`, initialized to `None`, acts as a cache. The function `get_keycloak_public_keys()`, defined at lines 13 through 34, fetches Keycloak's JSON Web Key Set from `KEYCLOAK_JWKS_URL` — falling back to deriving that URL from `KEYCLOAK_REALM_URL` if the former isn't set — and converts each key it finds into a usable RSA public key object, keyed by that key's `kid` identifier, using PyJWT's `RSAAlgorithm.from_jwk` helper.

The `require_jwt` decorator, defined at lines 36 through 93, is what every JSON API route ultimately depends on. When the Flask app is running with `TESTING` configuration enabled, it takes an important shortcut: rather than checking anything, it fabricates a fake set of claims granting every permission in the system and lets the request through unconditionally. This is precisely what allows the unit test suite in `tests/test_products.py` and `tests/test_stock.py` to call the API without ever constructing a real token. Outside of testing, the decorator reads the `Authorization` header, rejects anything that isn't a `Bearer` token, extracts the token's `kid` header to look up the matching public key (fetching and caching the full key set on first use), and then verifies the token's signature using the RS256 algorithm. On success, the decoded payload is attached to the request as `request.user_claims` for later code to consult. On any failure — an expired token, an invalid signature, a missing or unrecognized key — the request is rejected with a 401 response, and in every failure case `record_invalid_token()` increments a Prometheus counter.

Built directly on top of `require_jwt` is `require_scope`, a decorator factory defined at lines 95 through 106. Given a required scope string like `product:manage`, it wraps `require_jwt` and then checks whether that string appears in the `realm_access.roles` list inside the already-verified claims, returning a 403 if it doesn't. Every single route under `/api/` in this application is protected by some call to `require_scope`.

The UI side of the house works differently. `login_required`, at lines 108 through 127, is bypassed entirely under `TESTING` configuration just like `require_jwt` is. In production, it simply checks whether the key `'user'` exists in the Flask session — the same session populated by the OAuth callback described above — and redirects to the login page if it doesn't. When the session is present, it also sets `g.user` from the session's stored username or email, a detail that turns out to matter a great deal later, because it's exactly what the audit-logging system uses to record who made a given change.

Finally, `require_ui_scope`, at lines 130 through 148, is the UI-page equivalent of `require_scope`, but instead of checking a freshly-verified JWT, it checks the `user_scopes` list that was cached in the session at login time. If the required scope is missing, rather than returning a bare 403, it flashes a human-readable "Acceso denegado" message and redirects the visitor back to the dashboard.

This split between the two authorization mechanisms has a real consequence worth calling out explicitly: because the JSON API always re-verifies a fresh JWT on every call, a permission change made through the admin UI takes effect on the API side the very next time that user requests a new token. The UI, however, trusts whatever scopes were cached in the session cookie back when the user originally logged in, and won't reflect a permission change until that session is refreshed. This is precisely why `set_user_roles()` in `app/auth/keycloak_admin.py`, described next, also calls Keycloak's own `/users/{id}/logout` endpoint after changing someone's roles — forcibly ending their existing Keycloak session so that their next visit to the app forces a fresh login with the new permissions baked into a fresh token.

### Talking to Keycloak's Admin API

`app/auth/keycloak_admin.py` exists because this application deliberately keeps no user table of its own — every user account, password, and role assignment lives entirely inside Keycloak, and this file is the thin client that lets the Flask app read and modify that data through Keycloak's REST API.

Near the top, `MANAGEABLE_ROLES` lists the exact nine realm roles this application's admin screens are allowed to touch: the two group roles `group:employee` and `group:manager`, and the seven individual permission roles `product:view`, `product:manage`, `stock:view`, `stock:manage`, `report:view`, `audit:view`, and `user:manage`. Any role outside this list — Keycloak's own built-ins, for instance — is left alone by this code no matter what.

A handful of small helper functions resolve configuration: `_admin_base_url()` reads `KEYCLOAK_ADMIN_API_URL`; `_realm()` reads `KEYCLOAK_REALM`, defaulting to `inventory-realm`; `_token_url()` figures out the token endpoint on Keycloak's `master` realm, preferring an explicit `KEYCLOAK_ADMIN_TOKEN_URL` but able to derive it from `KEYCLOAK_TOKEN_URL` if that's absent; and `_app_token_url()` gives the token endpoint for this application's own realm, used when issuing a demonstration JWT rather than authenticating as an administrator.

`get_admin_access_token()`, at lines 65 through 92, performs a password grant against the `admin-cli` client using the Keycloak admin username and password from the environment, and is called fresh on every single Admin API request rather than being cached — a deliberate contrast with the public-key caching used for JWT verification, since admin tokens are short-lived and the extra round trip is a small price for always having a valid one. `_headers()` wraps that token into the standard `Authorization: Bearer` header plus a JSON content type, and `_realm_url(path)` builds the full URL for any given Admin API path under the configured realm.

From there, the file offers a fairly complete set of user-management primitives: `list_users()` lists users with an optional search filter; `get_user(user_id)` fetches a single user, raising a not-found error if Keycloak returns a 404; `find_user_id_by_username(username)` performs an exact-match lookup used right after creating a user, since Keycloak's creation endpoint doesn't return the new user's ID directly; `create_user()` posts a new user with a permanent (non-temporary) password and immediately-verified email, then looks up its ID and, if roles were supplied, calls `set_user_roles()` to assign them; `get_realm_roles()` lists every realm role that exists, not just the manageable ones; and `get_user_realm_roles(user_id)` lists the realm roles currently assigned to a specific user.

`_role_reps(role_names)`, a private helper, converts a list of role name strings into the `{id, name}` representations Keycloak's role-mapping endpoints require, raising an error if any requested name doesn't actually exist as a realm role. `set_user_roles(user_id, role_names)`, the most involved function in the file, diffs the user's current manageable roles against the desired set — carefully leaving any non-manageable roles the user might have completely untouched — removes whatever should no longer be assigned, adds whatever's newly requested, and then, as described above, makes a best-effort call to log the user out of their current Keycloak session so the change takes effect immediately rather than only on their next natural re-login.

`fetch_user_access_token(username, password)`, at lines 262 through 329, performs a password grant against the application's own public client to mint a genuine, usable JWT for a given user — this is exactly what powers the "issue a demonstration JWT" feature visible right after creating a new user and on each user's detail page. It decodes the resulting access token, again without verifying its signature since it just received it directly from Keycloak, and extracts the subject, username, email, filtered role list, and both the raw and human-readable issued-at and expiry timestamps. Notably, it deliberately excludes the refresh token from what it returns, since the admin panel only needs to demonstrate the access token, not maintain a long-lived session on the user's behalf. Finally, `user_summary(user, roles)` is a small formatting helper that normalizes a raw Keycloak user object and a role list into the flat dictionary shape used consistently across both the templates and the JSON API responses.

## Chapter 7 — Products

The `Product` model, defined in `app/products/models.py`, maps directly to the `products` table: an integer primary key, a name, a unique SKU, an optional description and category, a price stored as a fixed-point numeric value, an integer quantity defaulting to zero, an integer minimum-stock threshold also defaulting to zero, and a status string defaulting to `"active"`. Its `to_dict()` method is the single source of truth for how a product is serialized to JSON across the entire application — every API response involving a product, whether from the products blueprint itself, the reports blueprint, or the stock blueprint, ultimately calls this same method.

The products JSON API lives in `app/products/views.py`, mounted at `/api/products`. Listing products, at lines 35 through 68, supports searching by name or SKU using case-insensitive pattern matching, filtering by category, sorting by any of six whitelisted columns in either direction, and standard page-based pagination, returning the total count, page count, current page, and the serialized product list together. Creating a product, at lines 70 through 98, validates that a name, SKU, and price were all supplied, rejects the request outright if a product with that SKU already exists, and — on success — calls two telemetry helpers: one that increments a simple creation counter, and one that recomputes the live gauge of currently-active products from scratch by re-querying the database. Fetching a single product, at lines 143 through 152, and deleting one, at lines 154 through 169, are both straightforward, with deletion also triggering a recomputation of the active-product gauge afterward — because deleting a product changes that count too.

Updating a product, at lines 100 through 140, deserves closer attention because it's one of the places where the products and stock modules meet. The update is partial: only fields actually present in the incoming payload are changed, and if a new SKU would collide with a different existing product, the request is rejected. If the payload includes a new quantity that differs from the product's current quantity, the code calls `register_qty_change_movement()` — a function that actually lives in the stock module, not the products module — before committing the change, which creates a `StockMovement` row documenting that the quantity changed as a side effect of editing the product directly, rather than through the dedicated stock-movement endpoint. After the commit succeeds, a Prometheus counter records whether that implicit movement was an entry or an exit, based on whether the quantity went up or down.

Two Marshmallow schemas enforce these rules at the boundary of the API, before any view function body even runs, courtesy of flask-smorest's automatic request validation: `ProductSchema`, requiring name, SKU, and price and defaulting the remaining fields, is used for creation; `ProductUpdateSchema`, with every field optional, is used for partial updates. A validation failure short-circuits the request with an HTTP 422 response before any of the logic described above ever executes.

## Chapter 8 — Stock movements

The `StockMovement` model, in `app/stock/models.py`, records a single change in a product's quantity: which product it belongs to, who made the change, whether it was an `entry` or an `exit`, the quantity before and after the change, optional free-text notes, and a timestamp defaulting to the moment of creation. It declares a SQLAlchemy relationship back to `Product` with a cascading backref — `cascade='all, delete-orphan'` — meaning that if a product is ever deleted, every one of its movement records is deleted right along with it rather than being left behind as orphaned rows or having their foreign key nulled out. This ORM-level cascade is mirrored by an actual database-level foreign key constraint added later in the migration history, discussed in the migrations chapter.

Rather than duplicating movement-creation logic in every place it's needed, `app/stock/services.py` centralizes it into two small functions. `register_stock_movement()` simply constructs a `StockMovement` object and adds it to the current database session, deliberately leaving the decision of when to commit up to whoever called it, since the caller usually needs to make other changes — like updating the product's quantity — within the same transaction. `register_qty_change_movement()` builds on top of that by inferring whether a quantity change counts as an entry or an exit purely from whether the new value is higher or lower than the old one, and is the function called automatically whenever a product's quantity changes through some route other than the dedicated stock-movement endpoint, ensuring that every quantity change in the system, however it happens, leaves a trace.

The stock JSON API, in `app/stock/views.py` and mounted at `/api/stock`, exposes three endpoints. Registering a movement, at lines 21 through 67, validates that the referenced product exists, computes the resulting quantity, and — critically — refuses an exit movement that would drive the quantity below zero, returning a 400 error naming the current stock level. Fetching history, at lines 69 through 99, supports filtering by product, movement type, user, and a date range, returning the full matching list sorted newest-first rather than paginating it. Fetching alerts, at lines 102 through 114, returns every active product whose quantity has fallen to or below its configured minimum, wrapped in a slightly unusual shape: a list containing a single object with an `alert_count` and a `products` array, rather than the object being returned bare.

A dedicated Marshmallow schema, `StockMovementSchema`, requires a product ID, a movement type restricted to exactly `entry` or `exit`, and a positive quantity change, while defaulting notes to an empty string and the acting user to `"system"`.

## Chapter 9 — Reports

`app/reports/views.py` is deliberately the simplest module in the application: three read-only endpoints, all requiring the `report:view` permission, that compute aggregates over the products and stock-movement tables rather than exposing any new data of their own. Critical stock lists every active product whose quantity has fallen to or below its minimum threshold, sorted so the most critical shortages appear first. Top products lists active products sorted by quantity in descending order, capped by a `limit` query parameter that defaults to ten. Recent movements lists the most recent stock movements across all products, similarly capped by a `limit` parameter defaulting to twenty. None of these endpoints write anything; they exist purely to answer questions about data that other parts of the system already created.

## Chapter 10 — Auditing

The audit system is unusual in this codebase because it's never invoked directly by any route — it operates entirely through SQLAlchemy's event system, silently watching every change made to the `Product` and `StockMovement` tables and recording it without any of the application's own view functions needing to know it exists.

The `AuditLog` model, in `app/audit/models.py`, stores which table and record a change affected, whether the action was an insert, update, or delete, the old and new values as JSON, who made the change, and when. The actual capturing logic lives in `app/audit/listeners.py`. A small helper, `get_current_user()`, pulls the acting username from Flask's per-request `g` object, falling back to the literal string `"system"` if nothing set it — and as discussed in the authentication chapter, it's `login_required` in the UI, or the telemetry request hooks in `app/telemetry.py`, that populate `g.user` in the first place. Another helper, `json_serialize()`, converts values that can't natively live in a JSON column — `Decimal` prices, `datetime` timestamps — into JSON-friendly forms.

`capture_changes()`, bound to both the `after_insert` and `after_update` events on `Product` and `StockMovement`, does the actual work. For an update, it walks every attribute on the object being saved, checks SQLAlchemy's own change-tracking history to see which attributes actually differ from their previous value, and builds `old_values` and `new_values` dictionaries containing only those changed columns — if nothing actually changed, no audit row is written at all. For an insert, there's no meaningful "old" state, so `old_values` is left null and `new_values` captures every column's value. `capture_deletion()`, bound to the `after_delete` event, captures the entire row as it existed just before deletion. Both functions are careful to only fire for the `products` and `stock_movements` tables specifically, ignoring any other model that might somehow get wired to the same event in the future. `register_audit_listeners()`, called once at application startup from `app/main.py`, is what actually attaches all six of these listener bindings.

One subtlety worth understanding: because these are `after_*` events, the resulting audit row is added to the very same database session that's still in the middle of committing the original change, which means the audit row and the change that triggered it are committed — or rolled back — atomically, together, as a single transaction. There is no scenario in which a change succeeds but its audit trail is silently lost, or vice versa.

The read side, `app/audit/views.py`, is a small read-only JSON API mounted at `/api/audit`, all of it gated behind the `audit:view` permission: one endpoint lists audit entries with optional filters for table, record, and action type; two more fetch the audit history for a specific product or a specific stock movement by ID, each returning a 404 if no audit entries exist for that record at all.

## Chapter 11 — Managing users through Keycloak

`app/users/views.py` mounts a JSON API at `/api/users`, but it's worth restating plainly: there is no `users` table anywhere in this application's own database, and this module never touches Postgres. Every route here is a thin wrapper that delegates immediately to the Keycloak Admin client described in the authentication chapter. Listing users combines `list_users()` with a per-user lookup of their manageable roles; creating a user calls `create_user()` and then immediately calls `fetch_user_access_token()` so the very same response that confirms creation also hands back a working JWT for the new account; fetching a single user, updating their roles, and issuing them a fresh token all map directly onto the corresponding `keycloak_admin` functions. Every one of these routes requires the `user:manage` permission, and any failure surfaces as the message and status code carried by a `KeycloakAdminError`.

## Chapter 12 — The server-rendered UI routes

The bulk of `app/main.py`, from line 65 to its end around line 650, is a long sequence of route handlers that render HTML pages rather than JSON, all authenticated through the Flask session rather than a bearer token, using the `login_required` and `require_ui_scope` decorators described in the authentication chapter.

The home route renders the dashboard: counts of active products, products with low or critical stock, total movements ever recorded, and the five most recent movements. The products routes handle listing with search, sort, and pagination; a shared form template used for both creating and editing a product, distinguished by whether a product object was passed in; and a delete route. All of the product-mutating routes — new, edit, create, update, delete — require the `product:manage` permission, while simply viewing the list requires only being logged in. Several of these routes detect an `HX-Request` header, sent automatically by HTMX (loaded from a CDN in the base template), and when present, return just the relevant HTML fragment — a table body, say — instead of a full page, which is what lets search and pagination update part of the screen without a full reload.

The stock routes mirror this pattern: a history page with filters by movement type, date range, and product, and an update form that, on submission, validates the product exists, the movement type is valid, the quantity is a positive number, and — for exits — that enough stock actually exists, before mutating the product's quantity, creating a movement record, and committing both changes together in a single transaction, which is exactly the trigger point that produces two related audit-log entries at once, as described in the auditing chapter. The reports route requires `report:view` and renders three tables — critical stock, top products, and recent movements — computed directly against the database rather than by calling the JSON API internally. The audit route requires `audit:view` and additionally contains its own server-side rendered fallback: even if `require_ui_scope` somehow let a request through, the template itself checks the session's scope list again before showing anything, a deliberate piece of defense in depth.

The user-management routes under `/users` all require `user:manage` and are, again, thin wrappers around the same Keycloak Admin functions used by the JSON API — listing users, showing a creation form, handling that form's submission, showing a single user's detail page, updating their roles, and issuing them a token. The route that handles user creation is worth calling out specifically: after successfully creating the Keycloak account, it calls `fetch_user_access_token()` and passes the result straight into the template being rendered for that one response, rather than storing it in the session — a direct application of the lesson learned earlier about cookie size limits. The token is shown exactly once, on the page that confirms creation, and is never persisted anywhere after that.

Finally, `/health`, unlike every other UI route in this file, is protected by `require_jwt` rather than the session-based `login_required` — it's meant to be checked by infrastructure tooling with a bearer token, not by a logged-in human — and simply confirms the database is reachable by running a trivial `SELECT 1`.

## Chapter 13 — Telemetry: metrics, logs, and traces

`app/telemetry.py` is the file responsible for making the running application observable from the outside, and it does three distinct jobs: exposing Prometheus metrics, structuring every log line with consistent contextual fields, and exporting distributed traces.

A handful of Prometheus metric objects are created once, at module import time, and referenced from all over the codebase. A simple counter tracks the total number of products ever created. A counter labeled by movement type and product SKU tracks every stock movement. A gauge — set directly to a freshly computed count, rather than incremented — tracks how many products are currently active; it's recomputed from scratch by a small helper, `sync_active_products_total()`, every time a product is created, updated with a quantity change, or deleted, so it stays accurate rather than drifting. A counter labeled by source IP tracks authentication failures, incremented from the OAuth callback in `app/auth/views.py` whenever a token exchange fails. A plain counter tracks invalid tokens presented to the API, incremented from every failure branch inside `require_jwt` in `app/auth/middleware.py`. Small wrapper functions — `record_product_created()`, `record_stock_movement()`, `record_auth_failure()`, `record_invalid_token()`, and `sync_active_products_total()` — are what the rest of the codebase actually calls, keeping the metric objects themselves private to this module.

A second set of metrics is registered separately, inside `init_metrics()`, and only when `OTEL_ENABLED` is true: a counter and a histogram tracking every single HTTP request's method, endpoint, and status code, and its duration; and two gauges exposing the database connection pool's currently-checked-out connection count and its configured maximum size, computed live by calling directly into the SQLAlchemy engine's pool object rather than being manually updated anywhere. `init_metrics()` also registers the `/metrics` route itself, which simply calls Prometheus's own `generate_latest()` function against the default registry.

The logging half of the file centers on a custom formatter class that ensures every single log line, no matter where it's emitted from, carries the same set of contextual fields: a trace ID and span ID pulled from whatever OpenTelemetry span is currently active, falling back to a placeholder dash when there isn't one; and a correlation ID, a username, and an endpoint name, all pulled from Flask's per-request `g` object. A pair of request hooks, registered against the Flask app, populate that `g` object on every incoming request — generating a fresh correlation ID if the caller didn't supply one via an `X-Correlation-ID` header, recording the current endpoint, and pulling the logged-in username out of the session if one exists — and, when the request finishes, echo the correlation ID back in the response headers and log a single line summarizing the method, path, and final status code of the request. This is the exact log line visible in the container's output for literally every request the application ever serves.

The tracing half, when enabled, builds an OpenTelemetry tracer provider tagged with the configured service name, wires it to export spans in batches over OTLP to the configured endpoint, and instruments both Flask and SQLAlchemy automatically, meaning every incoming HTTP request and every SQL query executed against the database becomes a span without any manual instrumentation calls scattered through the business logic. A module-level flag guards against accidentally instrumenting everything a second time if the initialization function somehow gets called more than once in the same process.

## Chapter 14 — Templates

Every page in this application extends a single base template, which supplies the Tailwind CSS and HTMX libraries from a CDN, a navigation bar whose links are conditionally rendered based on the permission list cached in the session at login time, and a block that renders any flashed messages Flask's `flash()` function produced during the current request. ## Chapter 15 — The database's history, migration by migration

The schema wasn't designed all at once; it grew through four Alembic migrations, run by Flask-Migrate, each depending on the one before it. The first created the `products` table with its full set of columns as they exist today. The second created `stock_movements`, including its foreign key back to `products`, but without any cascading delete behavior yet. The third created `audit_logs`. The fourth and most recent migration doesn't add a table at all — it drops and recreates the foreign key between `stock_movements` and `products` specifically to add `ondelete='CASCADE'`, which is the database-level counterpart to the ORM-level cascade declared on the `StockMovement` model's relationship. Before this migration, deleting a product with existing movement history would have failed or behaved unexpectedly at the database level even though the ORM thought it knew what to do; after it, the two layers agree, and deleting a product cleanly removes its entire movement history along with it.

`migrations/env.py` is largely Flask-Migrate boilerplate that binds Alembic's migration runner to whichever SQLAlchemy engine the current Flask application is using, so the same migration files work whether the app is pointed at the development database, a CI database, or a test database. Running `flask db upgrade` walks this chain forward to the latest revision; a dedicated test file, described in the testing chapter, exists specifically to make sure this chain never accidentally branches into two divergent heads.

## Chapter 16 — The Keycloak realm

`keycloak/realm-export.json` is a complete snapshot of the identity provider's configuration, imported automatically the moment the Keycloak container starts, thanks to its `start-dev --import-realm` command and a read-only bind mount of this exact file.

The realm defines nine roles relevant to this application. Seven are simple, standalone permissions: viewing or managing products, viewing or managing stock, viewing reports, viewing the audit log, and managing users. The remaining two are composite roles that bundle several of the simple ones together: `group:employee` grants product viewing plus both stock permissions, representing a baseline worker; `group:manager` grants product management, user management, audit viewing, and report viewing, and additionally nests `group:employee` inside itself, so a manager automatically inherits everything an employee has as well as their own additional powers.

Two demonstration user accounts exist in the realm by default: `alice_worker`, assigned the `group:employee` role, and `kratos_boss`, assigned `group:manager`. Their password hashes as they exist in the exported JSON are not the plaintext `password123` you'll see referenced everywhere in this project's tests and documentation — they're whatever hashes happened to exist at export time, and nobody kept the corresponding plaintext. This is precisely why every environment that needs these accounts to actually be usable — the GitHub Actions pipeline, the Jenkins pipeline, and local end-to-end testing — runs a step that explicitly resets both accounts' passwords to `password123` immediately after Keycloak finishes importing the realm, using Keycloak's own `kcadm.sh` command-line tool.

The OAuth client this application uses, `flask-backend`, is configured as a public client, meaning it has no client secret and cannot be trusted to keep one confidential — appropriate for a client whose configuration ships inside a browser-facing single-page-ish application rather than living on a locked-down server. It has the standard authorization code flow enabled for interactive login, and direct access grants enabled as well, which is what allows the password-grant flow used by `fetch_user_access_token()` to work at all. Its registered redirect URI and post-logout redirect URI both point at `http://localhost:5000`, which is exactly why deploying this application under any other hostname requires updating this client's configuration in Keycloak, not just this application's own environment variables.

## Chapter 17 — Docker images

The application's own `Dockerfile` is short and unremarkable by design: it starts from a slim Python 3.12 base image, installs the pinned dependencies from `requirements.txt`, copies the entire repository in, exposes port 5000, and runs Flask's own built-in development server. It's worth noting explicitly that although `gunicorn` — a production-grade WSGI server — is listed among the dependencies, nothing in this repository actually launches it; every environment, including the "full stack" Compose file meant to resemble production most closely, runs the development server, complete with its own warning printed to the logs that it isn't meant for production use.

A second, more elaborate image lives under `jenkins/`, built specifically to run this project's CI pipeline. It starts from the official long-term-support Jenkins image, installs Git, `jq`, and Python, and — because the official image no longer ships a usable Docker client through the distribution's package manager — downloads static Docker CLI and Docker Compose binaries directly from their respective release pages. It bakes in a Jenkins Configuration-as-Code file that not only sets basic server preferences but actually defines the CI pipeline job itself as code, pointing at the repository through a `file:///workspace` Git remote — meaning the job exists automatically the first time the container starts, without anyone needing to click through Jenkins's own job-creation UI. A small entrypoint script runs before Jenkins itself starts, adjusting group permissions so the `jenkins` user inside the container can actually use the host's Docker socket once it's mounted in at runtime, and marking the bind-mounted repository as a Git "safe directory" since it isn't owned by that user.

## Chapter 18 — The two Docker Compose stacks

`docker-compose.yml` is the full development stack: every service described in the runtime-architecture chapter, including the entire observability suite. It mounts the whole repository into the `web` container as a live volume, so editing a file on the host is reflected inside the running container immediately. Three services — the end-to-end test runner, the security scanners, and Jenkins itself — are placed behind Compose profiles specifically so that a plain `docker compose up` doesn't start them; they have to be requested explicitly, either with a `--profile` flag or by running them directly with `docker compose run`.

`docker-compose.ci.yml` is deliberately much smaller: just a database, Keycloak, and the web application, with no observability services at all, since CI runs don't need dashboards. It differs from the full stack in a few important ways beyond simply being smaller. It includes an extra one-shot service, `keycloak-db-init`, whose entire job is to create a separate database named `keycloak` on the same Postgres instance before Keycloak itself starts — in this file, unlike the full development stack, Keycloak gets its own isolated database rather than sharing the application's own schema, a change made specifically to fix flakiness discovered while getting the CI pipeline stable. Both the database and Keycloak services here have real Docker health checks attached — a `pg_isready` probe for Postgres, and a raw TCP-based HTTP probe against Keycloak's own OpenID discovery endpoint — and the web service explicitly waits for both to report healthy, not just started, before it's allowed to come up. The web service's own startup command chains three steps together: first an extra Python-based wait for Keycloak's realm to be fully importable, then an automatic `flask db upgrade` to bring the schema up to date, and only then does it finally start serving requests — a level of automatic readiness the full development stack deliberately doesn't attempt, since a human running it locally is expected to run the migration step themselves.

## Chapter 19 — The helper scripts

A dozen or so scripts under `scripts/` exist to make both local development and continuous integration reliable rather than something you have to babysit by hand. `prepare-keycloak-e2e.sh` logs into the running Keycloak container as an administrator and resets the two demonstration accounts' passwords to a known value, as discussed in the Keycloak chapter — it's written to accept the compose file, project name, and compose binary as environment variables so the exact same script works whether it's being run against the full development stack, the CI stack, or a uniquely-named Jenkins build's own stack.

`wait-for-keycloak-realm.py` is a small Python script that polls Keycloak's OpenID discovery endpoint until it returns successfully or a configurable number of attempts is exhausted; it's used directly inside the CI web container's own startup command. `wait-for-services.sh` is a more general bash equivalent that can wait for an arbitrary list of named URLs, or, with no arguments at all, checks every core service in the full stack — Flask, Keycloak, Grafana, Prometheus, Alertmanager, Loki, Tempo, and Alloy — one after another. It relies on a small sourced helper file, `ci-http-check.sh`, which knows how to rewrite `localhost` into `host.docker.internal` and add an explicit `Host` header when a particular environment variable indicates the check is running from inside a container that can't resolve the host machine's own `localhost` the normal way — a situation that comes up specifically when Jenkins itself is running inside Docker.

`ci-verify-e2e-ready.sh` performs a similar readiness check but does it from inside the Compose network itself, by executing commands inside the already-running web container, rather than probing from whatever machine happens to be running the pipeline — this sidesteps port and hostname clashes that come up when multiple CI runs happen to overlap on the same shared Jenkins host. `ci-free-host-ports.sh` cleans up before a build even starts: it tears down any leftover Compose projects matching a recognizable CI naming pattern and stops any stray container still holding onto the ports this application needs, while carefully sparing the current build's own project if it's already partway through starting up. `jenkins-docker.sh` is a tiny wrapper that simply sets a few environment variables to known-good paths before running whatever command was actually passed to it, smoothing over path differences inside the custom Jenkins image.

`verify-stack.sh` is the most thorough of the readiness checks: beyond confirming every service is up, it asserts that Flask's metrics endpoint actually contains Prometheus-formatted data, that Prometheus itself reports every expected scrape target as healthy, that Grafana has at least four dashboards provisioned and specifically checks for each dashboard by its exact title, that Grafana has at least three datasources configured, that a real password grant against Keycloak for the manager demo account actually succeeds, and that an authenticated call to the products API returns success — in other words, it's an end-to-end proof that the entire observability and authentication story actually works together, not just that each service happened to start.

`start-observability.sh` is a convenience script for local development: it brings up the whole stack, waits for Grafana specifically, and prints out every service's local URL so you don't have to remember the port numbers. `run-security-scan.sh` brings up just the core application services, waits for Flask to respond, and then runs both the OWASP ZAP baseline scan and the pip-audit dependency scan through their respective Compose profiles, writing reports into a dedicated directory. `run-full-test-suite.sh` is the closest thing to running the entire CI pipeline by hand on your own machine: it builds the image, runs unit tests, contract tests, data-migration tests, a coverage pass, a security scan, and — depending on a few toggleable environment variables — the full Playwright end-to-end suite and a k6 smoke test against the entire stack including observability, cleaning up every Compose project it touches when it finishes, whether or not anything failed along the way.

## Chapter 20 — Sharing a live demo with the Cloudflare tunnel

Everything described so far assumes the browser and the server are the same machine — Keycloak's login page, its logout endpoint, its Admin API, all of it is wired around `localhost`. `scripts/cloudflare-tunnel.sh` exists to expose the running stack on a real, internet-reachable URL for a demo, without an account, without a domain, and — this is the part that took real care to get right — without breaking anything about how the app behaves when you go back to plain `localhost` afterward.

The mechanism it relies on is a Cloudflare "quick tunnel": the `cloudflared` binary opens an outbound connection from your machine to Cloudflare's edge network and gets back a free, randomly-named `https://something.trycloudflare.com` URL that proxies straight through to a local port. No signup, no configuration on Cloudflare's side, and the URL is different every single time you start one. The script downloads this binary once into a local `.tools/` folder if it isn't already installed, then starts one tunnel per port it needs to expose: `localhost:5000` for the Flask app, `localhost:8080` for Keycloak, and — only if it happens to already be running — `localhost:3000` for Grafana. Keycloak needs its own tunnel, separate from the app's, because the browser talks to it directly during login and logout; it's never proxied through Flask.

Once the tunnel URLs exist, the script writes them into a small, freshly generated file, `.env.cloudflare`, containing just the handful of variables that need to point somewhere other than `localhost` while the tunnel is active: the public app and Keycloak URLs, Keycloak's `KC_HOSTNAME_URL`/`KC_HOSTNAME_ADMIN_URL`, a `KC_PROXY_HEADERS` value telling Keycloak to trust forwarded headers, and the browser-facing `KEYCLOAK_ISSUER`/`KEYCLOAK_AUTHORIZE_URL`/`KEYCLOAK_LOGOUT_BASE` variables described in the environment-variables and authentication chapters. It then restarts just the `web` and `keycloak` containers with **two** environment files layered together — `docker compose --env-file .env --env-file .env.cloudflare up -d --no-deps keycloak web`. Docker Compose reads `--env-file` arguments left to right, with later files winning over earlier ones for any variable both define. `.env` supplies everything the app always needs regardless of how it's being accessed; `.env.cloudflare` supplies only the small set of overrides specific to "a tunnel happens to be active right now." Keeping them as two separate files, rather than merging the tunnel URLs into `.env` itself, means the generated file can be thrown away — and is, the moment you stop the tunnel — without ever touching your real configuration.

Every one of the Keycloak- and Grafana-facing environment variables this relies on already defaults to the exact same `localhost` value it always had, using Docker Compose's `${VAR:-default}` syntax — so a plain `docker compose up` with no tunnel involved behaves identically to how it always did. One default needed special handling: Keycloak treats an *empty* `KC_PROXY_HEADERS` value as invalid input and refuses to start, rather than treating it as "not configured" — so unlike the other variables, it has no fallback value at all when unset, only a real value supplied by `.env.cloudflare` when a tunnel actually needs it. Alongside this, `app/main.py` gained Werkzeug's `ProxyFix` middleware, which makes Flask trust the `X-Forwarded-Proto`/`X-Forwarded-Host` headers Cloudflare's proxy adds — without it, `url_for(..., _external=True)`, used to build the OAuth callback URL, would keep reporting the internal scheme and host instead of the public tunnel's, breaking the login redirect.

After restarting the containers, the script logs into Keycloak's own Admin API (the same mechanism described in the Keycloak-administration chapter) and updates the `flask-backend` client's allowed redirect URIs and post-logout redirect URIs to include **both** the new public URL **and** `localhost` at the same time, rather than replacing one with the other. This is the detail that makes `localhost:5000` keep working normally for the entire time a tunnel is active — Keycloak simply accepts either as valid, so whichever front door someone uses, the OAuth handshake completes successfully. Running `bash scripts/cloudflare-tunnel.sh stop` reverses the whole thing: it kills the `cloudflared` processes, deletes `.env.cloudflare`, restarts `web` and `keycloak` with only `.env` again, and calls the same Keycloak Admin API update one final time to reset the client back to a `localhost`-only configuration — so nothing is left pointing at a tunnel URL that no longer exists once you're done.

Two smaller, related fixes happened alongside this work rather than being part of the tunneling mechanism itself, but both mattered for the same underlying reason: exposing the app publicly meant paying closer attention to anything that had previously only been reachable by whoever was sitting at the keyboard. Grafana's dashboards used to be visible to any anonymous visitor with full administrator rights — harmless when only reachable on `localhost:3000`, not harmless once a link to it could be shared with anyone. It now requires a genuine login, configured through `GF_SECURITY_ADMIN_USER`/`GF_SECURITY_ADMIN_PASSWORD` in `.env` and defaulting to `admin`/`admin` for local development, and `verify-stack.sh` — used by both CI pipelines to confirm Grafana actually came up correctly — was updated to authenticate its own API calls and to read `.env` directly, so it always matches whatever password the containers were actually configured with rather than guessing. And the Keycloak logout bug described in the authentication chapter — an un-encoded, hardcoded-to-`localhost` redirect URL that produced a confusing "invalid URI" error the moment the app was reached from anywhere else — was fixed at the same time, since it was the very first thing that broke when this tunneling work began.

## Chapter 21 — The test suite

The test suite is deliberately layered, with each layer trading off speed against realism. The fastest layer, in `tests/test_products.py` and `tests/test_stock.py`, runs entirely against an in-memory SQLite database and relies on the `TESTING` configuration flag to bypass authentication entirely, as described in the authentication chapter — these tests cover the full range of ordinary product and stock behavior: creating, reading, updating, deleting, searching, filtering, sorting, paginating, rejecting duplicate SKUs, rejecting exits that would leave negative stock, and rejecting malformed requests. A shared fixture file, `tests/conftest.py`, is responsible for setting the database URL before the application module is even imported, since Python only runs a module's top-level code once per process.

A separate file, `tests/test_users.py`, tests the user-management API without ever making a real call to Keycloak at all — it uses Python's mocking library to substitute fake implementations of every Keycloak Admin function the view functions call, letting the tests focus purely on whether the Flask routes wire everything together correctly.

`tests/test_contract.py` takes a fundamentally different approach: rather than writing individual assertions by hand for every possible request shape, it loads the generated `openapi_spec.json` file and uses Schemathesis to automatically generate a wide range of request cases from that specification, asserting only that none of them ever produce a server error — a fuzz test rather than a fixed list of expectations, deliberately excluding the authentication routes from this fuzzing. Alongside the fuzzing, the same file also contains around fifteen conventional, fixed assertions covering specific expected status codes across products, stock, reports, audit, and health endpoints, giving the file both a broad but shallow fuzzed layer and a narrow but precise regression layer.

A third layer, under `tests/data/`, requires an actual Postgres database rather than SQLite and skips itself entirely if one isn't available. One file confirms the Alembic migration chain has exactly one head with no accidental branches and that every migration's declared predecessor genuinely exists; another confirms that duplicate SKUs are rejected at the database level itself, not merely by the application's own pre-insert check, that SKU uniqueness is case-sensitive, and that a null SKU is rejected outright.

The final and slowest layer, under `tests/e2e/`, drives an actual Chromium browser through Playwright against a genuinely running application and a genuinely running Keycloak instance. A shared fixture skips the entire layer gracefully if either service isn't actually reachable, rather than hanging or failing confusingly. A small helper function encapsulates the mechanics of a real Keycloak login — filling in the username and password fields on Keycloak's own login form and waiting for the browser to be redirected back to a URL that belongs to this application rather than to Keycloak — and raises a clear, descriptive error if Keycloak itself reports a login failure or if the whole process simply times out. On top of that helper, individual test files confirm that logging in as the ordinary employee account lands on the dashboard and correctly hides the audit and reports navigation links; that a manager can create a product through the real form and see it appear in the real product list; that a manager can register both an entry and an exit stock movement through the real form and see the resulting table rows reflect the correct type, quantity delta, and new stock level; and that the ordinary employee account, lacking the audit permission, sees no audit link in the navigation and is redirected away with an explicit denial message if they try to visit the audit page directly by URL. A test hook automatically captures a full-page screenshot of the browser the moment any end-to-end test fails, which is often the fastest way to understand what actually went wrong in a browser-driven test.

## Chapter 22 — Load and stress testing with k6

Three k6 scripts, plus one small shared helper, live under `tests/k6/`. The helper, `auth.js`, performs a password grant against Keycloak to obtain a bearer token, throwing an explicit error if the grant fails or the response is missing the token entirely, and every other script imports this helper rather than duplicating the authentication logic.

The smoke test is the lightest of the three: a single virtual user making just three iterations, each one checking that the products API and the metrics endpoint both respond successfully. This is the specific test both CI pipelines run as their very last step, after the entire stack — application, database, Keycloak, and the whole observability suite — has been brought up together, as a final proof that everything genuinely works end to end rather than merely having started without crashing.

The load test ramps a population of virtual users up to fifty over thirty seconds, holds them there for a full minute, and ramps back down, all of them repeatedly reading the products endpoint, with thresholds requiring that ninety-five percent of requests complete in under half a second and that fewer than one percent fail outright. The stress test pushes considerably harder and specifically targets the write path rather than reads: it ramps virtual users up through twenty, fifty, one hundred, and finally one hundred fifty over roughly two minutes, with each one repeatedly submitting randomized stock movements — a random product, a random direction, and a small random quantity — against the movement-creation endpoint, with correspondingly more lenient thresholds reflecting that writes are naturally more expensive than reads.

## Chapter 23 — Continuous integration on GitHub Actions

The workflow defined in `.github/workflows/ci.yml` triggers on every push and pull request targeting the `main` or `dev` branches, and is configured to automatically cancel any run that's been superseded by a newer push to the same branch, so pull requests updated rapidly don't queue up a backlog of stale runs.

The pipeline begins with a build job that does nothing more than install dependencies and confirm the application module can actually be imported without error — a cheap, fast check that catches syntax errors or missing dependencies before any slower job even starts. From there, three jobs run in parallel, all depending only on that initial build succeeding: a unit-test job running the fast SQLite-backed product and stock tests; an API and contract-test job running the Schemathesis-driven contract suite; and an integration-test job that spins up a genuine, ephemeral Postgres database as a GitHub Actions service container, applies the full migration chain against it, and runs the Postgres-dependent data-integrity tests.

Once all three of those finish successfully, a coverage job runs the entire non-end-to-end test suite together against another ephemeral Postgres instance, this time with coverage instrumentation enabled, and uploads the resulting coverage report as a downloadable artifact retained for two weeks. Independently, once the two faster test jobs finish, an end-to-end job spins up the full CI-flavored Compose stack, waits for both Keycloak and Flask to report ready, applies migrations, resets the demonstration accounts' passwords using the same commands found in `prepare-keycloak-e2e.sh` — duplicated inline here rather than calling the script directly — installs Playwright along with a Chromium browser, and runs the complete browser-driven test suite, dumping every container's logs if anything fails and always tearing the stack back down afterward regardless of outcome. A separate, simpler security job runs pip-audit directly against the dependency list and fails outright if it finds anything. Finally, a docker-build job, depending on the three parallel test jobs, confirms the production image can actually be built from the Dockerfile without error.

## Chapter 24 — Continuous integration on Jenkins

The `Jenkinsfile` describes a considerably more elaborate pipeline than the GitHub Actions workflow, built specifically to run against a bind-mounted copy of the repository rather than a fresh clone, which is why so many of its steps thread a host-path environment variable through to make sure bind-mounted volumes resolve correctly even though Jenkins itself is running as a container invoking sibling containers on the same Docker host. Each build generates its own uniquely-named set of Compose projects, tagged with the Jenkins build number, specifically so that concurrent or leftover builds on a shared Jenkins server never collide with one another over container or network names.

The pipeline checks out the repository, builds the application's Docker image, and runs a quick import sanity check inside a fresh container before running a preparatory step that frees up any host ports left behind by a previous, possibly-crashed build. Three test stages then run in parallel: unit tests and contract tests run directly inside the freshly built image with no external dependencies, while a third stage brings up its own dedicated, uniquely-named database-only Compose project, waits for Postgres to report ready, and runs the migration-and-data test suite against it, tearing that project down afterward regardless of whether the tests passed.

A coverage stage follows the same pattern — its own uniquely-named database project, brought up, waited on, tested against with coverage flags enabled, and torn down — followed by a straightforward pip-audit security stage running inside the built image. An end-to-end stage then brings up the full CI Compose stack with an explicit wait condition on every container reporting healthy, verifies readiness from inside the Compose network itself rather than from the Jenkins host, applies migrations, resets the demonstration accounts' passwords, and runs the full Playwright suite inside a container attached directly to the host's network so it can reach the application the same way a real browser would, dumping logs and tearing everything down afterward either way.

The most ambitious stage, run last before final image tagging, brings up the entire full development stack — application, database, Keycloak, and the complete observability suite together — generating a `.env` file with placeholder credentials if one doesn't already exist, waits for every single service to report ready, applies migrations, resets the demonstration passwords, runs the full `verify-stack.sh` check confirming that Grafana's dashboards and datasources are genuinely present and that authenticated API calls genuinely succeed, and finally runs the k6 smoke test against the whole thing. A top-level cleanup step, guaranteed to run whether the pipeline succeeded or failed, tears down every Compose project any stage might have created, ensuring a failed build never leaves orphaned containers quietly consuming the shared host's resources for the next build to trip over.

## Chapter 25 — The observability stack's configuration

Prometheus is configured to scrape every relevant target every fifteen seconds: itself, Tempo, Loki, Alloy, the Flask application's own `/metrics` endpoint, the host-level node exporter, and the Postgres exporter, while also loading alerting rule files from a dedicated rules directory and pointing its alert output at the Alertmanager service.

Those alerting rules are organized into three thematic groups. The infrastructure group watches host CPU usage, warning above eighty-five percent sustained for five minutes and escalating to critical above ninety-five percent sustained for three, watches host memory usage similarly, and watches the database connection pool specifically, firing a critical alert if the pool climbs above ninety percent of its configured capacity for more than three minutes — a rule that consumes the exact connection-pool gauges described in the telemetry chapter. The application group watches the overall error rate computed from the same request-counting metric described earlier, warning at an elevated but not yet severe error percentage and escalating to critical at a genuinely high one, and separately watches the ninety-fifth-percentile request latency, warning if it climbs above one second sustained for five minutes. The security group watches the authentication-failure counter for a sustained elevated rate that might indicate a brute-force attempt, watches for a sudden spike in invalid tokens presented to the API, and specifically watches for a large number of authentication failures originating from a single source IP address within a short window — three different angles on the same underlying signal, each tuned to catch a different pattern of abuse.

Alertmanager itself routes incoming alerts by the team and severity labels those same Prometheus rules attach, splitting them into separate critical and routine channels for the backend, infrastructure, and security teams, with an inhibition rule that suppresses a routine-severity alert if a critical one from the same alert group is already firing, so responders aren't flooded with redundant lower-priority noise during an active incident. As it stands today, every one of these receiver channels has an empty notification configuration — the routing logic is fully built out, but no actual Slack, email, or paging integration has been wired up yet, so alerts currently only ever surface inside Alertmanager's own web interface rather than reaching anyone proactively.

Grafana is provisioned, entirely through configuration files rather than manual setup, with three datasources — Prometheus as the default, Loki for logs, and Tempo for traces — and the Loki datasource is specifically configured to recognize a trace ID embedded in structured JSON log lines and turn it into a clickable link that jumps straight into the corresponding trace in Tempo, while the Tempo datasource is correspondingly configured to link back to Loki and to Prometheus's service map, making it possible to pivot fluidly between a slow trace, the exact log lines produced during that request, and the broader metrics context around it, all from within a single Grafana session. Four dashboards are provisioned automatically alongside these datasources, covering application latency and error rates, infrastructure resource usage, business-level product and stock-movement activity, and security-relevant authentication failures — the same four dashboards that `verify-stack.sh` checks for by name as part of confirming the whole stack actually came up correctly.

Grafana used to allow anonymous visitors full administrator access — convenient for a purely local dashboard nobody else could reach, but a real problem the moment Grafana might be exposed publicly. It now requires a genuine login (`GF_SECURITY_ADMIN_USER`/`GF_SECURITY_ADMIN_PASSWORD`, defaulting to `admin`/`admin` for local development), and `verify-stack.sh` was updated to authenticate its own Grafana API checks accordingly — the Cloudflare tunnel chapter covers why this change was made at the same time as the tunnel work.

## Chapter 26 — Security scanning

Two distinct security tools are wired into this project, each doing a genuinely different job. OWASP ZAP runs what's called a baseline scan — a purely passive check that crawls the running application and looks for common web-application weaknesses without ever attempting to actively exploit anything — against the application's own address inside the Compose network, writing both a human-readable HTML report and a machine-readable JSON report. Pip-audit, by contrast, doesn't touch the running application at all; it checks every pinned dependency in `requirements.txt` against known vulnerability databases. It's actually run in two subtly different ways depending on context: as a Compose service, it writes its findings to report files without failing anything, meant to be inspected afterward; inside both CI pipelines, it's run bare, with no output files, specifically so that any finding at all causes that pipeline stage to fail outright rather than merely being logged for later review.

## Chapter 27 — Generating the API documentation

The application's OpenAPI specification isn't written by hand — it's derived automatically from the Marshmallow schemas already attached to each blueprint's routes through flask-smorest's `arguments` decorator, which is the same mechanism responsible for validating incoming requests in the first place. A small standalone script, `generate_openapi_spec.py`, imports the fully configured application, asks flask-smorest for its assembled specification, and prints it as JSON; running this script and committing its output is how `openapi_spec.json` at the repository root gets kept current. This matters in a very concrete way: the contract-testing layer described in the testing chapter fuzzes requests based on exactly this committed file, not by introspecting the live application at test time, so if a route's schema changes without this file being regenerated and committed alongside it, the contract tests will silently keep testing against a stale, no-longer-accurate contract rather than catching the drift.

## Chapter 28 — Following a single piece of data from creation to observability

It's worth tracing one concrete example all the way through the system, because it ties together nearly every chapter above. Suppose a manager opens the stock-update form and registers an entry of five units against some product. The browser submits that form to the stock-update route in `app/main.py`, which first checks the manager is logged in and holds the `stock:manage` permission, then validates the product exists, the movement type is one of the two allowed values, and the quantity is a positive number. It computes the new quantity, adjusts the product object in memory, constructs a new `StockMovement` object through the shared service function, and commits both changes to the database in a single transaction.

That single commit is the moment several independent systems all react to the same event without any of them calling each other directly. SQLAlchemy's own event system, watching for exactly this kind of change, fires an `after_update` event for the product and an `after_insert` event for the new movement, and the audit listeners registered at startup catch both, writing two new rows into the audit log — one recording that the product's quantity changed and by how much, one recording that a new movement was created — each stamped with whichever username Flask's session-based authentication had already attached to the request. Separately, the view function itself calls a telemetry helper that increments the stock-movements-total Prometheus counter, labeled with the movement type and the product's SKU. And entirely independently of either of those, OpenTelemetry's automatic instrumentation has already been recording a trace span for the whole request and a nested span for the database commit itself, and the structured logging system has already tagged every log line produced during this request with a shared correlation ID and the currently active trace and span identifiers.

None of these systems know about each other. The audit listener doesn't know Prometheus exists; the telemetry counter doesn't know the audit log exists; neither knows anything about tracing. And yet, if you later wanted to understand this exact request — say, because it was unusually slow — you could open Grafana, find the slow trace in Tempo, follow its linked correlation ID straight into the exact log lines Loki captured for that specific request, and cross-reference the timestamp against a spike in the stock-movements-total counter in Prometheus, arriving at a complete picture of one request's life from three completely independent observability systems that were never explicitly told to cooperate — they simply all consistently tag everything with the same request-scoped identifiers, and that consistency is what makes the correlation possible after the fact.
